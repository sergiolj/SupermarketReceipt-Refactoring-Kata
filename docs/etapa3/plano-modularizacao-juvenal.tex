\section{Introdução e escopo}

Este plano descreve as estratégias de modularização, validação e melhoria da legibilidade aplicadas às classes \code{ShoppingCart}, \code{ProductQuantity}, \code{Product} e \code{ProductUnit}, pertencentes ao Grupo 2. O trabalho concentra-se na eliminação de estado redundante no carrinho de compras, no estabelecimento de regras de validação para os dados do domínio e no encapsulamento das regras relacionadas às unidades de medida.

O objetivo é reduzir inconsistências, melhorar a organização das responsabilidades e tornar as regras de domínio mais explícitas, preservando a compatibilidade com os demais componentes do sistema. Para isso, foram utilizadas técnicas do catálogo de refatorações de Fowler \cite{fowler2020}, especialmente \textit{Replace Derived Variable with Query}, além de validações nos construtores dos registros e encapsulamento de regras de negócio.

Este documento apresenta o diagnóstico das classes antes das alterações, a arquitetura considerada para o escopo do grupo, as estratégias aplicadas, os trechos de código anteriores e posteriores e os resultados observados após a execução dos testes.

\subsection{Desenho das estratégias de refatoração}

\begin{itemize}

\item \code{ShoppingCart}: a lista \code{items} passa a ser a única estrutura persistente responsável por armazenar as adições realizadas. O mapa de quantidades é construído quando solicitado, eliminando a necessidade de sincronizar duas estruturas durante cada operação de inclusão.

\item \code{ProductQuantity}: o construtor compacto do record passa a verificar se o produto é válido, se a quantidade é finita e não negativa e se a unidade permite a quantidade informada.

\item \code{Product}: o construtor compacto verifica se o nome não é nulo nem vazio e se a unidade foi informada.

\item \code{ProductUnit}: o método \code{acceptsQuantity(double quantity)} concentra a regra de compatibilidade entre a unidade e a quantidade. O método \code{isDiscrete()} também permite consultar diretamente se a unidade exige quantidades inteiras.

\end{itemize}

\textbf{Decisão tomada:} a validação de quantidades negativas e de valores não finitos permanece em \code{ProductQuantity}. O método \code{acceptsQuantity} de \code{ProductUnit} trata especificamente a compatibilidade entre a quantidade e a característica da unidade. Dessa forma, cada classe mantém uma responsabilidade bem definida.

\section{Antes e depois}

\subsection{Antes: estado duplicado no carrinho}

Na implementação original, o carrinho mantinha uma lista de adições individuais e um mapa com as quantidades agregadas. O método \code{addItemQuantity} precisava atualizar as duas estruturas:

\begin{lstlisting}
private final List<ProductQuantity> items = new ArrayList<>();
private final Map<Product, Double> productQuantities = new HashMap<>();

public void addItemQuantity(Product product, double quantity) {
    items.add(new ProductQuantity(product, quantity));

    if (productQuantities.containsKey(product)) {
        productQuantities.put(
            product,
            productQuantities.get(product) + quantity
        );
    } else {
        productQuantities.put(product, quantity);
    }
}
\end{lstlisting}

Essa abordagem mantinha informações derivadas em memória. Como as duas estruturas precisavam representar os mesmos dados, qualquer alteração na lógica de inclusão deveria preservar a sincronização entre elas.

\subsection{Depois: cálculo das quantidades sob demanda}

A refatoração removeu o mapa persistente e passou a construir a agregação a partir da lista de itens:

\begin{lstlisting}
private final List<ProductQuantity> items = new ArrayList<>();

Map<Product, Double> productQuantities() {
    Map<Product, Double> quantities = new HashMap<>();

    for (ProductQuantity item : items) {
        quantities.merge(
            item.product(),
            item.quantity(),
            Double::sum
        );
    }

    return Collections.unmodifiableMap(quantities);
}

public void addItemQuantity(Product product, double quantity) {
    items.add(new ProductQuantity(product, quantity));
}
\end{lstlisting}

Essa alteração aplica a técnica \textit{Replace Derived Variable with Query} \cite{fowler2020}. A lista passa a ser a fonte única de dados, enquanto o mapa representa uma consulta derivada.

O uso de \code{merge} simplifica a agregação das quantidades de produtos repetidos. O retorno de \code{Collections.unmodifiableMap} mantém a proteção contra modificações externas no resultado da consulta.

\subsection{Validação dos dados de produto e quantidade}

Antes da refatoração, os registros não possuíam validações próprias. A criação de objetos com informações inválidas era possível, mesmo quando essas informações não representavam um estado adequado do domínio.

Após a alteração, \code{Product} passou a validar seus dados:

\begin{lstlisting}
public record Product(String name, ProductUnit unit) {

    public Product {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException(
                "Product name cannot be null or blank"
            );
        }

        if (unit == null) {
            throw new IllegalArgumentException(
                "Product unit cannot be null"
            );
        }
    }
}
\end{lstlisting}

O registro \code{ProductQuantity} passou a concentrar as validações relacionadas à quantidade:

\begin{lstlisting}
public record ProductQuantity(
        Product product,
        double quantity) {

    public ProductQuantity {
        if (product == null) {
            throw new IllegalArgumentException(
                "Product cannot be null"
            );
        }

        if (!Double.isFinite(quantity) || quantity < 0) {
            throw new IllegalArgumentException(
                "Quantity must be finite and non-negative"
            );
        }

        if (!product.unit().acceptsQuantity(quantity)) {
            throw new IllegalArgumentException(
                "Quantity must be an integer for discrete units"
            );
        }
    }
}
\end{lstlisting}

Com essas verificações, os objetos passam a impedir a criação de estados incompatíveis com as regras estabelecidas para o domínio.

A quantidade zero foi mantida como válida. Para unidades fracionáveis, valores decimais continuam permitidos, desde que sejam finitos e não negativos. Para unidades discretas, somente quantidades inteiras são aceitas.

\subsection{Encapsulamento da regra de unidade}

Anteriormente, \code{ProductUnit} armazenava apenas uma característica booleana que identificava se a unidade era discreta:

\begin{lstlisting}
public enum ProductUnit {
    KILO(false), EACH(true);

    private final boolean discrete;

    ProductUnit(boolean discrete) {
        this.discrete = discrete;
    }
}
\end{lstlisting}

Após a refatoração, foram adicionados métodos que tornam essa característica acessível por meio de operações com significado no domínio:

\begin{lstlisting}
public enum ProductUnit {
    KILO(false), EACH(true);

    private final boolean discrete;

    ProductUnit(boolean discrete) {
        this.discrete = discrete;
    }

    public boolean isDiscrete() {
        return discrete;
    }

    public boolean acceptsQuantity(double quantity) {
        return !discrete || quantity == Math.floor(quantity);
    }
}
\end{lstlisting}

A unidade \code{KILO} aceita quantidades fracionárias, enquanto \code{EACH} exige valores inteiros. A regra deixa de depender de verificações externas sobre o atributo booleano e passa a ser expressa diretamente pelo método \code{acceptsQuantity}.

\section{Sequência de refatorações}

As alterações foram organizadas em etapas pequenas, permitindo verificar o comportamento do sistema durante o desenvolvimento. A estratégia segue a abordagem de evolução gradual de código legado descrita por Feathers \cite{feathers2013}.

\begin{enumerate}

\item Analisar a implementação original de \code{ShoppingCart}, identificando a duplicação entre a lista de itens e o mapa de quantidades agregadas.

\item Remover o mapa persistente e implementar o cálculo das quantidades sob demanda, utilizando a lista como fonte única de dados (\textit{Replace Derived Variable with Query}).

\item Preservar a imutabilidade das estruturas disponibilizadas pelos métodos \code{getItems()} e \code{productQuantities()}, evitando que consumidores externos alterem diretamente o estado do carrinho.

\item Implementar validações no construtor compacto de \code{Product}, impedindo nomes nulos, vazios ou compostos somente por espaços e unidades nulas.

\item Implementar validações no construtor compacto de \code{ProductQuantity}, verificando produto nulo, quantidades negativas, valores não finitos e compatibilidade com a unidade.

\item Encapsular em \code{ProductUnit} a regra de aceitação de quantidades, adicionando os métodos \code{isDiscrete()} e \code{acceptsQuantity(double quantity)}.

\item Criar testes unitários para as regras de validação dos registros e das unidades, além de executar a suíte completa para verificar a compatibilidade com os demais componentes.

\end{enumerate}

\section{Melhorias de legibilidade}

As alterações realizadas buscaram tornar o código mais expressivo, reduzir responsabilidades desnecessárias e aproximar as operações da linguagem do domínio.

\begin{itemize}

\item \textbf{Fonte única de dados:} a remoção do mapa persistente de \code{ShoppingCart} eliminou a necessidade de manter duas estruturas sincronizadas.

\item \textbf{Agregação expressiva:} o uso de \code{Map.merge} com \code{Double::sum} tornou a acumulação das quantidades mais direta e reduziu a quantidade de condicionais.

\item \textbf{Validação próxima dos dados:} os construtores compactos de \code{Product} e \code{ProductQuantity} impedem a criação de objetos inválidos no momento de sua construção.

\item \textbf{Encapsulamento da regra de unidade:} \code{acceptsQuantity} expressa diretamente a operação de verificar se uma unidade aceita determinada quantidade.

\item \textbf{Separação de responsabilidades:} cada classe passou a concentrar as regras relacionadas ao conceito que representa, evitando distribuir validações por diferentes componentes.

\item \textbf{Preservação da imutabilidade:} os métodos de consulta do carrinho continuam disponibilizando coleções não modificáveis, protegendo o estado interno.

\item \textbf{Testes orientados ao comportamento:} foram acrescentados testes que verificam situações válidas e inválidas, incluindo valores extremos e as diferenças entre unidades discretas e fracionáveis.

\end{itemize}

Essas melhorias estão alinhadas aos princípios de legibilidade e organização de responsabilidades apresentados por Martin \cite{martin2011}.

\section{Atualização após a execução}

\subsection{Situação dos passos}

As etapas previstas para o Grupo 2 foram concluídas:

\begin{itemize}

\item A duplicação de estado em \code{ShoppingCart} foi eliminada, mantendo a lista de itens como fonte única de dados.

\item O mapa de quantidades passou a ser calculado sob demanda, preservando a compatibilidade com os consumidores que utilizam o método \code{productQuantities()}.

\item Os métodos de consulta continuaram protegendo as estruturas internas por meio de coleções não modificáveis.

\item \code{Product} passou a validar o nome e a unidade informados durante sua construção.

\item \code{ProductQuantity} passou a validar a referência do produto, a quantidade e a compatibilidade entre quantidade e unidade.

\item \code{ProductUnit} passou a disponibilizar métodos que expressam diretamente as características das unidades e suas regras de aceitação.

\item Foram adicionados testes específicos para as validações de produto, quantidade e unidade, e a suíte completa foi executada sem erros.

\end{itemize}

\subsection{Decisões e divergências em relação à proposta}

Durante a implementação, algumas decisões foram tomadas para preservar a compatibilidade e manter o escopo da refatoração controlado.

\begin{itemize}

\item \textbf{Cálculo sob demanda:} a agregação das quantidades passou a percorrer a lista de itens sempre que o método \code{productQuantities()} é chamado. Essa decisão elimina a duplicação de estado, mas introduz um custo de processamento proporcional ao número de itens armazenados. Para o escopo atual, a simplificação e a redução do risco de inconsistência foram consideradas mais importantes do que manter uma estrutura agregada persistente.

\item \textbf{Quantidade zero permitida:} a validação rejeita valores negativos e não finitos, mas permite zero. Essa decisão preserva a possibilidade de representar uma quantidade nula sem introduzir uma restrição adicional que não era necessária para o comportamento existente.

\item \textbf{Validação de unidades discretas:} foi adotada a regra de que produtos vendidos por unidade (\code{EACH}) devem possuir quantidades inteiras. Produtos vendidos por peso (\code{KILO}) continuam aceitando valores fracionários.

\item \textbf{Tipo numérico preservado:} o tipo \code{double} foi mantido para evitar uma alteração de maior alcance nas interfaces utilizadas pelos grupos responsáveis por ofertas, caixa e recibo. A substituição por um tipo decimal mais adequado permanece como possibilidade de evolução futura.

\item \textbf{Organização em pacotes preservada:} as classes permaneceram em \code{dojo.supermarket.model}. A refatoração concentrou-se na organização interna e nas responsabilidades das classes, sem introduzir mudanças desnecessárias na estrutura de pacotes.

\end{itemize}

\section{Riscos e dependências entre grupos}

As alterações realizadas no Grupo 2 possuem pontos de integração com os demais componentes do sistema. Os principais riscos e suas respectivas estratégias de mitigação são:

\begin{itemize}

\item \textbf{Dependência do carrinho pelo Grupo 1:} o componente responsável pelas ofertas utiliza \code{productQuantities()} para obter as quantidades agregadas. A implementação manteve essa interface, preservando o contrato esperado e alterando somente a forma como o resultado é produzido.

\item \textbf{Dependência do carrinho pelo Grupo 3:} o processamento dos itens para composição do recibo utiliza a lista disponibilizada por \code{getItems()}. A estrutura e a ordem das adições foram preservadas, evitando mudanças no comportamento esperado pelo componente de impressão.

\item \textbf{Representação numérica:} a utilização de \code{double} permanece como uma limitação potencial para operações que exigem precisão decimal, especialmente em cenários financeiros. Uma futura substituição por \code{BigDecimal} exigiria alinhamento entre os grupos, pois afetaria as interfaces de quantidade, oferta, desconto e recibo.

\item \textbf{Regra de quantidade discreta:} a validação de quantidades inteiras para \code{EACH} representa uma regra de domínio adotada durante a refatoração. Alterações futuras nessa regra deverão considerar os requisitos de todos os componentes que utilizam produtos e quantidades.

\item \textbf{Custo da agregação sob demanda:} como o mapa é reconstruído a cada consulta, o processamento cresce proporcionalmente ao número de itens armazenados. Caso o volume de operações aumente significativamente, será necessário avaliar o desempenho dessa abordagem sem reintroduzir inconsistências de estado.

\item \textbf{Regressões de comportamento:} a preservação dos testes existentes e a inclusão de testes específicos para as novas validações reduzem o risco de alterações não intencionais. A execução da suíte completa deve continuar fazendo parte do processo de integração.

\end{itemize}
