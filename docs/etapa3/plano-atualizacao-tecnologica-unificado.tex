\section{Introdução e escopo}

Este documento reúne, em um único plano, as propostas de atualização tecnológica e as estratégias de evolução futura do sistema legado \textit{SupermarketReceipt Refactoring Kata}, na versão Java. O sistema simula um caixa de supermercado: recebe os produtos de um carrinho, aplica promoções semanais e emite uma nota fiscal. O diagnóstico que fundamenta o plano está no Relatório de Débito Técnico da Etapa 2.

A divisão do trabalho da Etapa 3 atribuiu a cada integrante um conjunto de classes, e cada conjunto gerou seu próprio plano, aqui consolidados:
\begin{itemize}
\item \textbf{Grupo 1} (Manuel Bahamonde Boulhosa Neto): \code{Teller}, \code{Offer} e \code{SpecialOfferType}, com o desafio de substituir a cadeia condicional de promoções por polimorfismo;
\item \textbf{Grupo 2} (Juvenal Rosa Alves Costa Junior): \code{ShoppingCart}, \code{ProductQuantity}, \code{Product} e \code{ProductUnit}, com os desafios do estado duplicado do carrinho e da quantidade em \code{double};
\item \textbf{Grupo 3} (Sérgio Lopes Júnior): \code{Receipt}, \code{ReceiptItem}, \code{Discount}, \code{ReceiptPrinter} e o catálogo, com os desafios da impressão sem testes, da lista de descontos mutável e da lista longa de parâmetros.
\end{itemize}

O texto distingue o que foi \textbf{efetivamente implementado} do que permanece como \textbf{proposta futura}. A situação descrita corresponde ao estado da \code{main} em 23 de novembro de 2026, já com as mudanças feitas em conjunto pelos três grupos. Cada fase e estratégia indica entre parênteses o grupo de origem.

O problema mais concreto do código legado era o arredondamento do dinheiro em \code{double}. Uma nota com um item de 1,00 e um desconto de $-0{,}995$ era impressa pelo código original assim:
\begin{lstlisting}[language={}]
toothbrush      1.00
x(toothbrush)  -1.00

Total:          0.01
\end{lstlisting}
As linhas somam 0,00, mas o total impresso era 0,01, porque cada linha era arredondada separadamente a partir de um \code{double}. Com o tipo \code{Money}, o mesmo caso passou a imprimir \code{Total: 0.00}, resultado verificado executando o código atual. Em uma nota fiscal real, essa divergência não seria aceitável.

\section{Estratégias para evolução futura}

\subsection{Ofertas extensíveis e oferta de pacote (Grupo 1)}
Antes da refatoração, criar um tipo de oferta exigia alterar o \textit{enum} e editar o método \code{handleOffers}. Com cada oferta em uma estratégia própria, um novo tipo é uma nova classe ou uma expressão \textit{lambda}, sem alterar as existentes (GAMMA \textit{et al}., 2000). Isso foi demonstrado em teste. A oferta de pacote (\textit{bundle}), prevista no enunciado do \textit{kata}, foi implementada em \code{BundleOffer}, como tipo à parte, porque envolve vários produtos enquanto a estratégia trabalha com um produto por vez.

\subsection{Cadastro de ofertas separado do caixa e configuração externa (Grupo 1)}
O cadastro de ofertas saiu do \code{Teller} para \code{SpecialOffers}, compartilhável entre caixas. Como as promoções mudam toda semana, a evolução natural é carregá-las de uma fonte externa (arquivo JSON ou YAML), com período de validade, para evitar recompilar o sistema a cada semana, e, depois, migrar essa fonte para um banco relacional. O valor das ofertas ainda entra pela API pública como \code{double}, e deve passar a ser \code{Money}.

\subsection{Dinheiro e quantidade como tipos do domínio (Grupos 1, 2 e 3)}
\code{Money} e \code{Quantity} foram introduzidos uma única vez, em conjunto, porque atravessam carrinho, ofertas, nota e catálogo. Eles são a base para evoluções fiscais futuras, como impostos por item, arredondamento conforme a legislação e moedas diferentes. Para quantidades, uma evolução possível é distinguir tipos para unidades inteiras e para pesos fracionados, o que tornaria a regra de \code{ProductUnit} ainda mais explícita; isso só se justifica se o domínio ficar mais complexo.

\subsection{Agregação do carrinho e regras de domínio (Grupo 2)}
O carrinho calcula as quantidades agregadas sob demanda a partir da lista de itens, o que elimina o risco de divergência entre estruturas. O custo é proporcional ao número de itens a cada consulta; só se justifica reintroduzir uma estrutura agregada com atualização centralizada se medições de desempenho mostrarem necessidade, para não acrescentar complexidade prematura. As validações podem ser ampliadas (restrições de comercialização, precisão permitida para pesos), sempre próximas dos conceitos que representam.

\subsection{Novos formatos de saída e separação entre modelo e apresentação (Grupo 3)}
A interface \code{ReceiptPrinterFormatter} separa o contrato das implementações, no padrão \textit{Strategy}. O formato HTML já foi implementado; JSON para uma API ou PDF seriam novas classes, sem alterar o printer de texto (MARTIN, 2011). A formatação de preço e quantidade está em \code{ReceiptFormat}, compartilhada por todos os formatos. Se surgir um terceiro formato com estrutura comum, o esqueleto pode ser extraído em uma classe abstrata (\textit{Template Method}). O método \code{ReceiptFormat.total()} devolve o rótulo \code{"Total: "}, que é um detalhe do layout em texto, e deve voltar para o \code{ReceiptPrinter}.

\subsection{Catálogo real (Grupo 3)}
Hoje só existe o catálogo de testes. Uma implementação de produção, com persistência em banco, deve usar o produto completo (nome e unidade) como chave, e tratar produto ausente com uma exceção de domínio.

\subsection{Organização modular (Grupos 1, 2 e 3)}
Os três planos convergem para um \textbf{monólito modular}, com pacotes por responsabilidade e sem serviços independentes: o sistema tem cerca de 700 linhas de produção, e a quebra em microsserviços não se justifica (SOMMERVILLE, 2019). A divisão proposta está no plano de modularização.

\subsection{Qualidade automatizada (Grupos 1 e 2)}
Complementar os testes unitários com testes baseados em propriedades (agregação de quantidades, validações de unidade), adotar análise estática e publicar a cobertura no CI, para acompanhar a evolução da qualidade e detectar regressões.

\subsection{Exposição como serviço (Grupos 1 e 3)}
Para uso por um ponto de venda, o cálculo da nota pode ser exposto por uma API HTTP, com um formato JSON implementado como mais uma estratégia de saída.

\section{Indicadores de sucesso}

\begin{itemize}
\item Complexidade ciclomática do maior método de ofertas: de 13 (\code{handleOffers}) para 4 (\textbf{atingido}; Grupo 1).
\item Nova oferta criada sem editar as classes existentes (\textbf{atingido}, demonstrado em \code{TellerTest}; Grupo 1).
\item Carrinho com estrutura única de dados (\textbf{atingido}; Grupo 2) e validações nos construtores de produto e quantidade (\textbf{atingido}; Grupo 2).
\item Precisão decimal para dinheiro e quantidade (\textbf{atingido} com \code{Money} e \code{Quantity}; Grupos 1, 2 e 3).
\item Total impresso igual à soma das linhas (\textbf{atingido}: o caso de $-0{,}995$ imprime \code{Total: 0.00}; Grupo 3).
\item Novo formato de saída sem alterar o printer de texto (\textbf{atingido} com o HTML; Grupo 3).
\item Cobertura de 100\% das linhas e dos \textit{branches} e todos os testes passando no CI (\textbf{atingido}: 124 testes; todos os grupos).
\item Análise estática no CI (\textbf{pendente}), Maven Wrapper (\textbf{pendente}) e Javadoc em todas as classes públicas (\textbf{parcial}).
\end{itemize}
