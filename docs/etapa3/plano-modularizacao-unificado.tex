\section{Introdução e escopo}

Este plano reúne, em um único documento, a estratégia de modularização e de melhoria de legibilidade e complexidade aplicada às classes do \textit{SupermarketReceipt Refactoring Kata} pelos três grupos de trabalho: ofertas e caixa (Grupo 1: \code{Teller}, \code{Offer}, \code{SpecialOfferType} e a lógica de \code{handleOffers}), carrinho e quantidades (Grupo 2: \code{ShoppingCart}, \code{ProductQuantity}, \code{Product}, \code{ProductUnit}) e nota fiscal e impressão (Grupo 3: \code{Receipt}, \code{ReceiptItem}, \code{Discount}, \code{ReceiptPrinter} e o catálogo).

O objetivo é reduzir a complexidade ciclomática, separar responsabilidades e tornar as regras mais explícitas, sem alterar o comportamento observável, seguindo o catálogo de refatorações de Fowler (2020) e as recomendações de Martin (2011). Antes de qualquer alteração, o comportamento atual foi registrado com testes de caracterização, inclusive os defeitos do legado (FEATHERS, 2013), e padrões de projeto foram aplicados onde havia seleção de comportamento por tipo (GAMMA \textit{et al}., 2000).

O documento foi \textbf{atualizado após a execução} dos três grupos: os trechos de código da seção 4 correspondem ao estado atual da \code{main}, a seção 8 registra o que diverge dos planos originais e a seção 7 traz os resultados medidos. Cada item indica o grupo de origem.

\section{Arquitetura-alvo}

\subsection{Pacotes propostos}

Os três planos originais convergiam para uma separação em pacotes por responsabilidade, com nomes ligeiramente diferentes. A proposta unificada abaixo reconcilia as três versões e define uma regra de dependência em um único sentido.

\noindent\textbf{Regra de dependência:} \code{printing} depende de \code{receipt}; \code{receipt} depende só de \code{model}; \code{offer} depende de \code{model} e de \code{receipt} (porque \code{SpecialOffers} registra descontos na nota); \code{checkout} depende de \code{offer}, \code{receipt} e \code{model}. Nenhum pacote depende de \code{checkout} ou de \code{printing}, o que evita ciclos. Duas consequências práticas: \code{SupermarketCatalog} e \code{Discount} ficam em \code{model}, porque são usados por vários pacotes, e métodos hoje visíveis só dentro do pacote (\code{SpecialOffers.applyTo}, \code{ShoppingCart.getItems} e \code{productQuantities}) precisarão se tornar públicos quando as classes forem separadas.

\subsection{Responsabilidades por componente}

\begin{itemize}
\item \textbf{Ofertas (Grupo 1):} \code{OfferStrategy} define o contrato de uma promoção para um produto; cada implementação concentra uma regra; \code{OfferStrategies} converte \code{SpecialOfferType} em estratégia, preservando a API pública do \code{Teller}; \code{SpecialOffers} guarda as ofertas e as aplica ao carrinho; \code{BundleOffer} trata ofertas que olham vários produtos.
\item \textbf{Carrinho e produto (Grupo 2):} \code{ShoppingCart} guarda os itens adicionados e calcula as quantidades agregadas sob demanda; \code{Product} e \code{ProductQuantity} validam seus dados na criação; \code{ProductUnit.acceptsQuantity} concentra a regra de unidade discreta; \code{Quantity} representa a quantidade com precisão decimal.
\item \textbf{Nota e impressão (Grupo 3):} \code{Receipt} guarda itens e descontos, calcula o total e expõe as duas listas apenas como visões imutáveis; \code{ReceiptItem} calcula o total do item e responde sobre si mesmo; \code{ReceiptFormat} concentra a formatação de preço e quantidade; \code{ReceiptPrinterFormatter} é o contrato de qualquer formato de saída.
\end{itemize}

\textbf{Decisões de projeto:} \code{OfferStrategy} trabalha com um produto por vez, e o pacote é um tipo à parte; o record anêmico \code{Offer} foi removido, porque o mapa em \code{SpecialOffers} cumpre seu papel; e \code{Discount} permanece em \code{model}, porque é criado pelas ofertas e aparece em classes dos três grupos.

\section{Antes e depois}

\subsection{Regra de oferta (Grupo 1)}
Antes: a regra do leve 3 e pague 2 ficava no meio de uma cadeia condicional em \code{ShoppingCart.handleOffers}.
\begin{lstlisting}
int x = 1;
if (offer.offerType() == SpecialOfferType.THREE_FOR_TWO) {
    x = 3;
} else if (offer.offerType() == SpecialOfferType.TWO_FOR_AMOUNT) {
    x = 2;
    if (quantityAsInt >= 2) { /* ... */ }
} if (offer.offerType() == SpecialOfferType.FIVE_FOR_AMOUNT) {
    x = 5;
}
int numberOfXs = quantityAsInt / x;
if (offer.offerType() == SpecialOfferType.THREE_FOR_TWO && quantityAsInt > 2) {
    double discountAmount = quantity * unitPrice
        - ((numberOfXs * 2 * unitPrice) + quantityAsInt % 3 * unitPrice);
    discount = new Discount(p, "3 for 2", -discountAmount);
}
\end{lstlisting}
Depois: cada oferta em sua classe, com constantes nomeadas e os tipos \code{Quantity} e \code{Money}.
\begin{lstlisting}
public Optional<Discount> discountFor(Product product, Quantity quantity, Money unitPrice) {
    int units = quantity.wholeUnits();
    if (units < GROUP_SIZE) {
        return Optional.empty();
    }
    int completeGroups = units / GROUP_SIZE;
    Money fullPrice = unitPrice.times(quantity);
    Money payable = unitPrice.times(completeGroups * PAID_PER_GROUP + units % GROUP_SIZE);
    return Optional.of(new Discount(product, "3 for 2", payable.minus(fullPrice)));
}
\end{lstlisting}

\subsection{Estado do carrinho (Grupo 2)}
Antes: duas estruturas que precisavam ser atualizadas juntas.
\begin{lstlisting}
private final List<ProductQuantity> items = new ArrayList<>();
private final Map<Product, Double> productQuantities = new HashMap<>();

public void addItemQuantity(Product product, double quantity) {
    items.add(new ProductQuantity(product, quantity));
    if (productQuantities.containsKey(product)) {
        productQuantities.put(product, productQuantities.get(product) + quantity);
    } else {
        productQuantities.put(product, quantity);
    }
}
\end{lstlisting}
Depois: a lista é a fonte única, e o mapa é uma consulta derivada (\textit{Replace Derived Variable with Query}).
\begin{lstlisting}
private final List<ProductQuantity> items = new ArrayList<>();

Map<Product, Quantity> productQuantities() {
    Map<Product, Quantity> quantities = new HashMap<>();
    for (ProductQuantity item : items) {
        quantities.merge(item.product(), item.quantity(), Quantity::plus);
    }
    return Collections.unmodifiableMap(quantities);
}
\end{lstlisting}

\subsection{Validação e regra de unidade (Grupo 2)}
Antes, \code{ProductQuantity} era um \textit{record} sem nenhuma regra. Depois, a criação de um objeto inválido falha, e a regra de unidade fica em \code{ProductUnit}.
\begin{lstlisting}
public record ProductQuantity(Product product, Quantity quantity) {
    public ProductQuantity {
        if (product == null) {
            throw new IllegalArgumentException("Product cannot be null");
        }
        if (quantity == null) {
            throw new IllegalArgumentException("Quantity cannot be null");
        }
        if (!product.unit().acceptsQuantity(quantity)) {
            throw new IllegalArgumentException("Quantity must be an integer for discrete units");
        }
    }
}

public boolean acceptsQuantity(Quantity quantity) {
    return !discrete || quantity.isWholeNumber();
}
\end{lstlisting}

private static String presentQuantity(ReceiptItem item) {

\subsection{Tipos de valor (transversal)}
Antes, o dinheiro e a quantidade eram \code{double} em todo o domínio, o que gerava erros de arredondamento binário (0,1 mais 0,2 não resulta exatamente em 0,3). Depois, \code{Money} (duas casas, \textit{half-up}) e \code{Quantity} (três casas) tornam a soma exata e concentram as regras de arredondamento e do \textit{cast} para \code{int} (\code{wholeUnits()}).

\section{Melhorias de legibilidade}

\begin{itemize}
\item \textbf{Regras em classes próprias:} cada oferta é uma classe pequena, e o método principal do printer passou a ser um sumário (itens, descontos, linha em branco, total) (MARTIN, 2011).
\item \textbf{Nomes e constantes:} eliminação de \code{x} e \code{numberOfXs} em favor de \code{GROUP_SIZE} e \code{completeGroups}; constantes no lugar de literais de formato e de largura; \code{formatLineWithWhitespace} passou a \code{formatLineLeftAndRightAlignment}.
\item \textbf{Fonte única de dados e validação próxima dos dados:} o carrinho guarda só a lista; construtores impedem objetos inválidos.
\item \textbf{Condições com nome de intenção:} \code{hasSingleQuantity()} no lugar de comparações soltas.
\item \textbf{Encapsulamento:} regra de unidade em \code{ProductUnit}, listas imutáveis na nota, formatação em \code{ReceiptFormat}.
\item \textbf{Testes orientados ao comportamento:} nomeados pelo que verificam, com valores esperados literais; comentários desatualizados e código comentado removidos.
\item \textbf{Documentação:} Javadoc nas classes novas de ofertas, valores e HTML (10 de 23 classes de produção).
\end{itemize}

\section{Decisões e divergências em relação aos planos}

\begin{itemize}
\item \textbf{Pacotes adiados.} Os três planos previram a divisão em pacotes, mas nenhum a executou: mover as estratégias para outro pacote enquanto \code{Teller} e \code{Discount} compartilham o pacote original criaria dependência circular. A proposta unificada da seção 3 resolve o problema com a regra de dependência em um sentido, e a mudança deve ser feita em um único \textit{commit}, quando não houver \textit{branches} abertos nas mesmas classes.
\item \textbf{Tipo numérico: de preservado a adotado.} O Grupo 2 havia preservado \code{double} para manter a compatibilidade e o Grupo 3 o registrava como pendência conjunta. A troca foi feita pelos três em conjunto, e de forma atômica: \code{Money} e, depois, \code{Quantity}.
\item \textbf{Defeito introduzido e corrigido (Grupo 3).} Ao nomear a condição da linha de quantidade, \code{item.quantity() != 1} foi trocada por \code{item.quantity() > 1}, e quantidades menores que 1 (por exemplo, 0,5 kg) deixaram de imprimir a linha. A suíte continuou verde porque nenhum teste usava quantidade abaixo de 1. O defeito foi encontrado na revisão, o teste \code{printsLessThanOneKilo} o reproduziu e a condição original foi restaurada. Uma suíte verde só protege o que ela cobre.
\item \textbf{Mudanças de comportamento intencionais.} (i) Total do item derivado (Grupo 3): três testes que informavam totais incoerentes com quantidade e preço tiveram o valor esperado corrigido. (ii) Arredondamento ao centavo (\code{Money}): 10\% de uma escova de 0,99 passou de 0,099 para 0,10, e as descrições mostram duas casas (``2 for 1.50''). (iii) Validação na criação (Grupo 2): objetos inválidos falham com \code{IllegalArgumentException}.
\item \textbf{Decisões do Grupo 2.} A agregação sob demanda troca simplicidade por custo proporcional ao número de itens; a quantidade zero foi mantida como válida; produtos por unidade exigem quantidades inteiras.
\item \textbf{Formato HTML.} O plano do Grupo 3 registrava \code{ReceiptPrinterHtml} como esqueleto que devolvia \code{null}; ele foi implementado depois, com escape de caracteres especiais e testes.
\end{itemize}

\section{Riscos e dependências entre grupos}

\begin{itemize}
\item \textbf{Remoção de \code{handleOffers} (Grupo 1 sobre o Grupo 2):} a única mudança em \code{ShoppingCart} feita pelo Grupo 1. Mitigação: aviso ao grupo e \textit{pull request} pequeno.
\item \textbf{Consumidores do carrinho:} as ofertas usam \code{productQuantities()} e a nota usa \code{getItems()}. As interfaces foram mantidas, e a ordem das adições, preservada.
\item \textbf{Assinatura de \code{addProduct} (Grupo 3 sobre o Grupo 1):} a mudança de quatro para três parâmetros alterou a chamada no \code{Teller}, tratada com aviso e \textit{pull request} pequeno.
\item \textbf{\code{ProductUnit} e \code{isDiscrete()}:} o \code{ReceiptItem} usa esse método sem alterá-lo (\textit{Hide Delegate}). Qualquer mudança no tipo de quantidade deve preservá-lo.
\item \textbf{Tipos \code{Money} e \code{Quantity}:} afetaram arquivos dos três grupos. Mitigação: mudança atômica, com todos os testes atualizados.
\item \textbf{Mudança de pacotes:} afeta classes e testes dos três grupos; deve ser um único \textit{commit} sem alteração de comportamento.
\item \textbf{\code{FakeCatalog} compartilhado:} usado por quase todos os testes. Mudar a exceção de produto ausente (L-25) exige revisar os testes que dependem dela.
\item \textbf{Custo da agregação sob demanda e regressões:} manter a abordagem enquanto não houver evidência de problema de desempenho, e manter a suíte completa no CI.
\end{itemize}
